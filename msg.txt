feat(scoring): analysts' rules of 21 Sep -- Proof of Address never unresolved, premises number decides the bill match, GST-mismatch means the portal account, Zigram namesakes dismissed, annex shows options only, findings carry every caveat; perf: OCR upright-first early stop, API retries

Four decisions from the analysts and the founder on 21 Sep, applied
together.

1. Proof of Address never scores "unresolved" (resolvers.py,
   config/scoring_model.json, review_sheet.py, review/graph.py)
   Every POA row resolves to one of its options; missing, unreadable or
   incomparable evidence lands on the row's 0 option with the reason in the
   workbook's Evidence column.
   - POA-02: no bill readable, no GST address, or nothing comparable ->
     not_match.
   - POA-01: a bill in a third party's name with no rental agreement, or no
     deed / agreement / bill at all -> address_mismatch, relabelled "Not
     established -- premises proof missing, in a third party's name, or for
     a different address". No new option was added.
   - POA-03 follows: rented/leased + minor bill -> minor_discrepancy;
     otherwise not_match. POA-05: premises not established -> absent (owned
     stays N/A). POA-04: no Udyam number and no lookup -> not_valid.
   - The POA rows' workbook dropdowns no longer offer "unresolved" and the
     validator rejects it there (NO_UNRESOLVED_CATEGORIES); an LLM
     correction whose proposed_value is not one of the row's options is
     escalated instead of applied (_bucket_values) -- it would have scored
     as unresolved.

2. Electricity bill vs GST address: the premises number decides
   (resolvers.py, founder's rule)
   - A different plot / door / house number is a different address -- 155
     Saraswati Nagar is not 157 -- "not match", even with the locality and
     PIN agreeing. Sri Laxmi Steel (plot 382 vs 384/385, same estate):
     minor_discrepancy -> not_match.
   - The same number with locality and PIN agreeing (or the PIN absent on a
     side) is a match; the same number with the locality/street named
     differently, or the PIN off (B R Trading 711201/711202), is a minor
     discrepancy.
   - No comparable number: agreeing locality or PIN is a minor discrepancy
     (partial evidence), nothing in common is not match. A keyworded plot
     number of any length ("Plot 15") now counts as the premises identity
     (PlotComparison.agree).

3. Bank verification: "GST mismatch" means the GST portal registers a
   different account (resolvers.py)
   A vendor with no portal screenshot is always "Penny drop successful +
   GST unavailable" (2). A penny-drop holder name that matches none of the
   vendor's names is a CRITICAL note for the findings, never the mismatch
   bucket -- and the holder name is now compared with the legal name, the
   trade name and the partners (a proprietorship's account is routinely in
   the trade name: Sri Laxmi Steel, 1 -> 2). _name_match ignores corporate
   suffixes and M/S ("MANGAL IRON PVT.LTD." = "MANGAL IRON PRIVATE
   LIMITED").

4. Zigram namesakes are dismissed on the response's own evidence
   (aml/zigram_screening.py, resolvers.py, review/tools.py)
   A fresh Zigram call for B R Trading Co (PAN AADFB0389G, West Bengal)
   returned the same 19 rows on Maharashtra's GST non-genuine-dealer list --
   every row a different Maharashtra firm with its own GSTIN
   (27EBDPG9119N1Z7 x13, 27CGYPG7879K1Z5, 27AKLPD7385G1ZU,
   27CRYPV9120P5ZB). Zigram matched the name and ignored the PAN we sent;
   the analysts' own Zigram case called "MS R R TRADING COMPANY" a 99%
   exact match for "B.R. TRADING COMPANY". Two gates before a row counts:
   the listed record's PAN / GSTIN differs from the vendor's, or the
   matched name fails the initials-aware name check. Dismissals are counted
   on AML-01's note ("Zigram namesakes dismissed: 19 row(s) on '...' --
   listed entity's PAN ... is not the vendor's ..."). Rows with neither a
   PAN nor a usable name still stand for the analyst (Skandan's ESIC hit).
   B R Trading Co AML 4/5 -> 5/5, header "AML Cleared".

5. Report layout (report/build_context.py)
   - The scoring annex shows the scored option and nothing else; an
     unresolved row reads "Not determined" (required) or "N/A -- not
     applicable" (conditional).
   - Findings & Observations carries everything else: why a row was not
     determined, and every caveat a resolver attached to a scored row (GAP,
     WARNING, CRITICAL, DISCREPANCY, NOTE, CONFLICT, dismissed namesakes),
     one line each -- the marker sentence of the note, abbreviation-aware
     ("plot/survey no. 382" is not a sentence end).

6. OCR time (extract/ocr.py) and API retries (finoscale_api/client.py)
   - The rotation search reads upright first and stops when that pass is
     plainly good (>= 120 characters kept at >= 0.4 confidence, mean
     confidence >= 0.6); the 180 / 90 / 270 passes -- three quarters of a
     run's OCR time, 20-40 minutes on a 12-page folder -- run only for a
     page that does not clear the bar (a sideways scan reads as a few
     garbled tokens). OCR_EARLY_STOP_CHARS / OCR_EARLY_STOP_CONF.
   - A read timeout is retried once with double the timeout (Ongrid
     fetch-detailed took > 30 s on MANGAL IRON and seven parameters went
     unresolved); a 429 is retried once after 5 s (the API sends no
     Retry-After; a burst limit clears, a quota does not and the second 429
     is raised as before). Counted in cache_stats["retried"].

7. Three report inconsistencies the reviewer caught on the first run with
   the above (SYM Singhal Alloys, 21 Sep): "Year Incorporated" now uses the
   firm's own formation date (Udyam / COI) and falls back to the GST year
   only without one (2017 -> 2003); a multi-state PAN reads "Multiple
   active GST registrations -- multi-state operation" instead of "single
   clean registration"; an ownership row driven by an unreadable bill says
   the bill could not be read, not that it is for a different address.
